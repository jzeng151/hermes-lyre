# Write for ears

The reader listens to this document with a screen reader. They hear it one line at a time, in order, and move around by headings. Write so it makes sense heard aloud.

Lyre already rewrites your replies so screen readers can read them. This skill is about the document itself: clear structure and words carry further than any rewrite.

## Structure

- Start with one or two sentences that say what the document is and what the reader will get from it.
- Use headings for every section. Screen-reader users jump between headings, so each heading should name its section plainly: "Install", "Settings", "Known problems". Avoid clever or vague headings.
- Keep heading levels in order. Do not skip from level 1 to level 3.
- Keep paragraphs short: two to four sentences. Put one idea in each.
- Put the most important point first in each section and each paragraph.

## Lists

- Use a list for three or more parallel items, and say how many there are first when it helps: "There are three steps."
- Keep list items short. A list item that runs over two sentences is usually a paragraph.
- Nest lists at most one level deep. Deep nesting is hard to follow by ear.
- Number steps that must happen in order.

## Tables

- Use a table only when the reader needs to compare values across rows and columns.
- Introduce every table in a sentence first: what it compares and how many rows it has.
- Keep tables small: a few columns, short cells, and a header row.
- Never use a table for layout or for a list of steps. Write the steps as a numbered list.
- If a table would have one or two columns, write it as a list instead.

## Links

- Give every link a label that says where it goes: "the installation guide", not "here" or "this link".
- Do not paste a long address in the middle of a sentence. Give the label in the sentence and the address after it, or at the end of the section.

## Emoji, symbols and decoration

- Do not use emoji for decoration or as bullet points. A screen reader reads each one by name.
- If status matters, say it in words: "passed", "failed", "warning".
- Avoid ASCII art, box drawing, rows of dashes or equals signs, and repeated punctuation used as dividers. Use a heading instead.
- Avoid symbols that stand for words. Write "and", "about", "to" and "versus" rather than "&", "~", "->" and "vs.".

## Code

- Say what a code block is before it: "Run this command in a terminal:".
- Keep code blocks for code. Do not put prose or tables in them.
- After a long block, say what it did or what to expect.

## Images and diagrams

- Give every image alt text that says what it shows and why it matters.
- Describe diagrams in words next to them. A diagram should never be the only place a fact appears.

## Words

- Spell out abbreviations the first time you use them.
- Write numbers and units clearly: "5 minutes", not "5m".
- Prefer plain words and active sentences.
- Do not rely on position or colour: "the red item" and "see above" mean nothing when listening. Name the thing instead.

## Before you finish

Read the document as if you could only hear it, one line at a time. Check that each heading makes sense on its own, every table and code block is introduced, and no line is only symbols.
